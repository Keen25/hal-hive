## R1 — F5 REVERT: DirectoryDiscovery back to independent NdjMode eval (reviewer consensus)
Round 1 routed `DirectoryDiscovery` through the cached `ClientConnections.IsNonDomainJoined`
seam (+`Lazy`). **Szabolcs rejects that coupling** — `DirectoryDiscovery._current` could be
consulted before `ClientConnections.Initialize()` and observe the default `Windows`, wrongly
selecting `Win32DirectoryDiscovery` in NDJ. The user has decided to **defer to Szabolcs**.

**Revert `Service/Source/Service/Domains/DirectoryDiscovery.cs` to independent evaluation:**
- `CreateCurrent()` reads `bool ndj = ActiveRoles.Common.Services.ActiveDirectory.Configuration.NdjMode.IsEnabled();`
  again (NOT `ClientConnections.IsNonDomainJoined`).
- Restore `_current` to `private static readonly IDirectoryDiscovery _current = CreateCurrent();`
  and `public static IDirectoryDiscovery Current => _current;` (drop the `Lazy<>`). Szabolcs
  explicitly considers the once-per-process `static readonly` init a non-issue.
- KEEP an improved doc comment (do NOT go back to the bare original). Document:
  (a) discovery evaluates `NdjMode.IsEnabled()` **independently by design** — this is the
  order-safe choice because coupling to `ClientConnections.IsNonDomainJoined` would risk
  reading the default before `Initialize()` runs;
  (b) both this site and `ClientConnections` read the same env/file, so they agree except in a
  negligible mid-startup toggle window (`ndj-endpoints.json` appearing/disappearing between the
  two evaluations), which does not occur in practice;
  (c) init-order note: mode is fixed once at class init; changing the env/file takes effect only
  after a service restart.

## R2 — Item 5 (MED): double-`Initialize()` orphans pools — dispose-before-replace
`ApplyNdjComposition` (in `ClientConnections.cs`) overwrites `RequestPool`/`DirSyncPool`
without disposing the previous instances. A second `Initialize()` in NDJ mode leaks the old
pools; a re-init NDJ→Windows leaves stale pools referenced.
**Fix:** at the very start of `ApplyNdjComposition`, dispose+null any existing pools before
(re)deriving mode and building new ones. Reuse the existing `DisposePools()` helper:
```csharp
internal static void ApplyNdjComposition(System.Func<OneIdentity.Ldap.ILdapClient> ldapClientFactory)
{
    DisposePools();   // dispose-before-replace: guards a second Initialize() from orphaning pools
    IdentityMode = ...NdjMode.IsEnabled() ? IdentityProviderMode.Ldap : IdentityProviderMode.Windows;
    if (IdentityMode == IdentityProviderMode.Ldap) { ...build both pools... }
}
```
Add a test in `ClientConnectionsCompositionTests`:
`ApplyNdjComposition_CalledTwiceInNdj_DisposesPreviousPools` — first call builds a pool over a
tracked fake client; second NDJ call must dispose the first pool's client (verify the first
`Mock<ILdapClient>.As<IDisposable>()` got `Dispose()` `Times.Once()`), and pools remain non-null.
(Restore env + `DisposePools()` in cleanup as the existing tests do.)
